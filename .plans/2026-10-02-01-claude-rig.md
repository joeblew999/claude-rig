# 2026-10-02-01-claude-rig.md

The first plan for claude-rig: what it is, how it is laid out, and the order to build it in.

## What it is

claude-rig turns any machine into a Claude coding machine that you can control from the Claude app.

It works on:

- macOS
- Linux
- Windows (a physical PC or a UTM virtual machine)

One run installs the tools, applies the global Claude config, and starts a Claude session that stays running, so the machine shows up in the Claude app.

## Rules that apply to everything

1. **Idempotent.** Every step checks first and acts only if something is missing or wrong. Running it twice in a row changes nothing the second time. A run that stopped halfway is fixed by running it again.
2. **No secrets in the repo.** Tokens are passed in at run time (from fnox on the Mac doing the push), never committed, never baked into a VM image.
3. **The Mac is the source of truth for the Claude config.** The repo holds a copy captured from the Mac's global `~/.claude`.
4. **Never destroy local state.** Back up before the first change, merge rather than overwrite.

## Layout

```
claude-rig/
  bootstrap.sh        # macOS + Linux: install git and mise, then run the rig
  bootstrap.ps1       # Windows: same job, using winget
                      # (the only two native scripts; everything else is nushell)
  mise.toml           # the repo's own tasks (rig, apply, capture, lint)
  mise/
    claude-rig.toml   # every tool, the same list on all three OSes
  claude/
    settings.json     # captured from the Mac, remote control on
    CLAUDE.md
    skills/
  tasks/
    rig.nu            # the main run: tools, Claude Code, Claude config
    apply.nu          # apply claude/ to this machine's ~/.claude
    enroll.nu         # log in, and set up the always-on session
    session.nu        # the always-on session itself, run by pitchfork
    capture.nu        # copy the Mac's ~/.claude into claude/
    push.nu           # rig a remote machine over SSH
    doctor.nu         # show what is set up and what is missing
    lib.nu            # shared helpers
```

## What one run does

Each step checks before it acts.

1. **Base tools.** Install git and mise if they are missing. This is the only step written per OS (the Command Line Tools and the mise installer on macOS, the distro package manager and the mise installer on Linux, winget on Windows). mise then fetches nushell, and every later step is the same nushell code on all three.
2. **Everything else.** The rig copies `mise/claude-rig.toml` to `~/.config/mise/conf.d/claude-rig.toml` and runs `mise install`, which brings in gh, nushell, fnox and the rest. The tools are then on hand in every folder, and the machine's own mise config is left alone.
3. **Claude Code.** Install with the native installer if `claude` is missing: `install.sh` on macOS and Linux, `install.ps1` on Windows. If it is installed, leave it (Claude Code updates itself).
4. **Claude config.** Apply `claude/` to `~/.claude` (see the next section).
5. **Login.** If the machine is not logged in with a claude.ai account, run `claude auth login`: it prints a link, the owner approves it on any device and pastes the code back. Remote Control needs this full login. An API key or a `claude setup-token` token can only make model requests, so neither can be used. With no terminal to ask on, the step is skipped and the rig says how to finish.
6. **Session.** pitchfork runs `tasks/session.nu`, which starts `claude remote-control` in the work folder (`~/work`) under the machine's name. pitchfork restarts it if it stops and starts it again after a reboot (launchd on macOS, systemd on Linux, both set up by `pitchfork boot enable`). Windows needs a scheduled task for the start at boot, which is not built yet.

## Applying the Claude config to a machine that already has one

- **Backup.** The first time the rig touches a machine, it copies everything it could change (`settings.json`, `CLAUDE.md`, `skills/`, `agents/`, `commands/`, `hooks/`) to `~/.claude.rig-backup-<date>`. It does this once, not on every run. Session history and the rest of `~/.claude` are never touched, so they are not copied.
- **settings.json is merged, not replaced.** The keys the rig owns (remote control and the rest of the captured config) are set. Keys that exist only on that machine are kept. Lists keep the rig's entries and add any that exist only on that machine.
- **Skills are synced folder by folder.** Rig skills are added or updated. Extra skills that only exist on that machine are left alone. The rig records what it installed in `~/.claude/.rig-manifest`, so a skill later removed on the Mac is removed from the machine too. The same goes for `agents/`, `commands/` and `hooks/`.
- **CLAUDE.md** is replaced, but only if it differs, and only after the backup exists.
- **`~/.claude.json` is never copied or overwritten.** It holds login state. The rig writes one thing to it: the approval for the work folder the rig itself created, because a service has no terminal for Claude to ask on.

## Capturing the config from the Mac

`mise run capture`, run on the Mac:

- copies `~/.claude/settings.json`, `~/.claude/CLAUDE.md` and `~/.claude/skills/` into `claude/` (plus `agents/`, `commands/` and `hooks/` when they exist)
- leaves out `skills/synced/`, which the Claude account fills in on each machine
- drops the settings that only make sense on the Mac (`permissions.additionalDirectories`, `sandbox.network.allowUnixSockets`), and stops with an error if any path under the Mac's home folder is still in the copy
- strips anything that looks like a secret, and stops with an error if it finds one it cannot strip safely
- never copies `~/.claude.json`
- shows a diff, so the change goes in through a normal commit and PR

Re-run it whenever the Mac's config changes. Every machine picks up the change on its next run.

## Ways onto a machine

| Machine | How |
|---|---|
| Any machine with SSH | `mise run push user@host` from the Mac. It copies the bootstrap over, passes the tokens in that session, and runs it. |
| Sitting at the machine | One line: `curl -fsSL <raw-url>/bootstrap.sh \| sh` or `irm <raw-url>/bootstrap.ps1 \| iex` |
| UTM Windows VM | irgo-winvm runs the bootstrap before it takes the golden image, then passes tokens into each clone after it boots. |
| Existing office Windows PC | Turn on OpenSSH Server once, then use `push`. |

Note: the repo is public, so the one-line raw URL works with no token. That also means everything `capture` commits is published, so its secret and machine-path checks must pass before anything lands in `claude/`.

## Doctor and dry run

- `doctor` lists each step, whether it is done, and the command to finish it.
- `--dry-run` on the main run prints what would change and changes nothing.

## Things to check along the way

- **Windows ARM64.** The UTM VMs are Windows 11 ARM64. Claude Code supports ARM64; confirm every tool in `mise.toml` has an ARM64 Windows build.
- **Fresh Windows installs** can have an old or missing winget until App Installer updates. `bootstrap.ps1` checks and updates it first.
- **Unattended permissions.** Decide per machine how much Claude may do without asking. Broad permissions only on a dedicated user or a VM that can be rolled back.

## Build order

Each step lands as its own PR.

1. `capture` task, and the first captured `claude/` from the Mac (run by the local Claude agent on the Mac).
2. `bootstrap.sh` + `mise.toml` + config apply, tested on macOS (a second Mac or a macOS UTM VM).
3. Linux: the same script, plus the systemd service.
4. `bootstrap.ps1` + the Windows task, tested on a UTM Windows VM.
5. `push` task over SSH, tested on the office Windows PC.
6. Hook into irgo-winvm's golden image step, and decide how the one-line URL is served.
7. `doctor` and `--dry-run` across all three OSes.
